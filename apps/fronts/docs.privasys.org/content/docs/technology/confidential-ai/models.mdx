A Confidential AI instance serves up to three models on one GPU, each in its own vLLM engine inside the enclave:

| Task | Serves | Example |
| --- | --- | --- |
| Generate | `/v1/chat/completions`, `/v1/messages`, `/v1/completions` | Qwen3.6 35B-A3B (FP8) |
| Embed | `/v1/embeddings` | Qwen3 Embedding 0.6B |
| Rerank | `/v1/rerank` | Qwen3 Reranker 0.6B |

The chat model takes most of the GPU memory; the embedding model and the reranker share what is left. The embedding model and reranker are optional. [Privasys Drive](/solutions/drive/memory-for-chat) uses them to index and search your documents inside the same trust boundary as the model that reads them.

## Loading

The app owner declares the whole model set in one call:

```http
POST /v1/models/load
Authorization: Bearer <owner token>

{
  "model": "Qwen/Qwen3.6-35B-A3B-FP8",
  "embedding_model": "Qwen/Qwen3-Embedding-0.6B",
  "rerank_model": "Qwen/Qwen3-Reranker-0.6B",
  "max_model_len": 262144,
  "kv_cache_dtype": "fp8"
}
```

A model is a Hugging Face repository id or a directory on a read-only model disk. A repository is downloaded once, inside the enclave, into the app's encrypted volume; later loads read it from there. The declared set is saved on the same volume, and the instance loads it again by itself after every restart, so the owner never has to resend it.

The generate engine is loaded first and serves chat as soon as it is up; the embedding model and the reranker follow. Weights are read with eight threads in parallel, which matters for a 35 GB model.

Only the app owner or an admin can load or unload models. Callers of the API cannot change which weights answer them.

### Reasoning and tool calling

The instance configures vLLM's reasoning and tool-call parsers from the model family, so tool calls arrive as structured `tool_calls` (OpenAI) or `tool_use` blocks (Messages), and a reasoning model's thinking is returned separately from its answer.

## Attesting the model

Each model's identity is a digest of every file vLLM reads. For a model on a verity-protected disk it is the disk's dm-verity root hash. Otherwise it is the SHA-256 of a manifest listing the SHA-256 of each file, in the format `sha256sum` prints, sorted by path. You can recompute it from the same files:

```bash
cd <model directory> && find -L . -type f ! -name '.*' | sed 's|^\./||' | LC_ALL=C sort | xargs sha256sum | sha256sum
```

A Hugging Face weight file is stored under its SHA-256. The instance checks each file's content against that name the first time the file is used, and a file that does not match fails the load: the instance never serves weights that are not what they claim to be.

The digests are published two ways:

- The chat model's digest is stamped into the instance's TLS certificate as OID `1.3.6.1.4.1.65230.5.4.5`, next to the hardware quote. A client sees it in the same handshake that proves the code.
- Every model is listed at `GET /.well-known/served-models`, read over the same attested connection, with its digest and the list of files and hashes the digest covers. A client can check each file's hash against the one the model's publisher lists (Hugging Face shows the SHA-256 of every weight file), then recompute the digest itself. An app that depends on a particular model pins this manifest: a different embedding model, for example, would make Drive's index meaningless.

A change of model is therefore visible to every client and fails closed for every pinned dependant.

## Readiness

`GET /v1/models/status` reports each model's state (`loading`, `ready`, `error`) and load progress. `GET /readiness` returns `200` only when all configured models are ready, which is what monitoring should watch; chat traffic does not wait for it.
