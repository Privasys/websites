A **vault** is a container of keys that you own, backed by the [vault constellation](/solutions/enclave-vaults/overview): a set of SGX enclaves where secrets are Shamir-split and threshold keys are generated by the vaults together; other keys live whole inside one vault. The platform never sees key material. You authenticate; the platform authors the key's owner-bound policy and mints a short-lived grant; the CLI then creates the material **directly on the constellation** over mutual RA-TLS. The control plane never touches key material.

## Vaults

```sh
privasys vault create my-vault
privasys vault list
privasys vault rm <vault-id>
```

The number of vaults you may create is set by your plan.

## Keys

```sh
privasys vault key create my-vault signer --type p256    # ECDSA P-256 signing key
privasys vault key create my-vault wrapper --type aes    # AES-256-GCM wrapping key
privasys vault key create my-vault release --type ed25519 # threshold Ed25519 signing key
privasys vault key create my-vault seed                  # a Shamir-split secret (default)
privasys vault key list my-vault
```

Four key types:

- **`p256`**: a managed signing key. Generated client-side, created whole on one vault, **signed in-enclave**; the private half never leaves and the key is non-exportable.
- **`aes`**: a managed wrapping key. Encrypt and decrypt happen in-enclave; non-exportable.
- **`ed25519`**: a threshold signing key. The vaults generate it together and each keeps one share, so no vault and not the CLI ever holds the key. Any `--threshold` of the vaults sign together (the default is the constellation's threshold), and the result is a standard Ed25519 signature (`EdDSA`). Never exportable. Needs CLI v0.57.0 or later. See [threshold Ed25519 keys](/solutions/enclave-vaults/architecture#pattern-c-threshold-ed25519-keys-frosted25519).
- **`secret`** (default): opaque bytes you provide (or random), Shamir-split across the constellation, exportable by the owner.

## Use a key

```sh
# Sign (the private key never leaves the enclave)
privasys vault key sign my-vault signer "message"
privasys vault key sign my-vault signer <64-hex-digest> --prehashed   # CKM_ECDSA: sign a SHA-256 digest raw
privasys vault key public my-vault signer

# Encrypt / decrypt under an AES key (in-enclave)
privasys vault key wrap my-vault wrapper "plaintext"
privasys vault key unwrap my-vault wrapper --ciphertext <b64> --iv <b64>
```

`--prehashed` signs a pre-computed 32-byte SHA-256 digest without re-hashing. That is the form TLS stacks and code signers need (PKCS#11 `CKM_ECDSA`). It applies to `p256` keys only: an Ed25519 key signs the message itself.

For an `ed25519` key, `sign` asks the vaults to sign together; each checks the key's policy against your session and audits the call. `public` returns an OKP JWK (`"kty": "OKP"`, `"crv": "Ed25519"`, `x`), and the JSON output of `create` (`--format json`) carries it as `public_key_b64url`.

## Rotate, audit, delete

```sh
privasys vault key rotate my-vault signer     # new primary version; old versions still verify/unwrap
privasys vault key audit my-vault signer      # the key's tamper-evident audit log, read from the vault
privasys vault key rm my-vault signer         # destroys the material on the constellation
```

`rm` destroys the material, and the vaults remember the name until the key's original expiry, so the same name cannot come back with a new value in the meantime.

Every new key asks for your approval in the wallet before its rules change and before it is promoted, deleted or exported (approval by default); a policy can opt out only by saying so explicitly. A key created before approval by default keeps its rules, and as its owner you can always add the passkey approval to them: that tightening is always open to the owner, unless the key's rules are frozen.

Rotation creates a new primary version with fresh material. Old versions are retained so data signed or wrapped under them still verifies and unwraps; pin one with `--version`. Rotating an `ed25519` key gives it a **new** public key. To keep the same public key, renew it instead:

```sh
privasys vault key renew my-vault release                # same key and public key, fresh shares, a fresh 90 days
privasys vault key renew my-vault release --threshold 3  # and change how many vaults must sign
```

Renewal moves the key to the active constellation and needs your approval in the wallet, which names the vaults and the vault build the key goes to. It needs CLI v0.58.1 or later (v0.58.3 or later on the test platform), and a key created on vault v0.39.0 or later. Since v0.58.5 the wallet notification names the key and its key vault. `rm` on an `ed25519` key destroys its share on every vault.

## User secrets

`secrets` is the lightweight path for a personal key that is not inside a named vault:

```sh
privasys secrets create api-seed              # random material; Shamir-split; you own it
privasys secrets export api-seed --out ./key  # local file only, never printed; WebAuthn step-up
privasys secrets rm api-seed                  # destroy every copy you own; cannot be undone
```

`secrets rm` finds every copy of the secret you own, on every constellation and in every generation a renewal left, and destroys each one, newest first, with your approval in the wallet for each where the secret asks for it. Declining one stops there. At the end it asks the vaults again and says whether anything of that name is still held. It needs CLI v0.59.0 or later. Vaults that keep a record of deleted keys hold a deleted secret's name until the date it would have expired, so a new secret needs another name until then.

Export is deliberately guarded: the material is written to a local file with `0600` permissions, only a fingerprint is shown, and the vault requires a fresh WebAuthn approval bound to that exact export, so a leaked session token alone cannot exfiltrate a key.

## The REST facade and standards

`privasys vault serve` runs a local, Azure Key Vault-shaped REST facade over a vault, so existing tooling can use the vHSM unchanged:

```sh
privasys vault serve my-vault
```

On top of that facade Privasys ships enterprise interop: a **KMIP 2.1 gateway** and a **PKCS#11 3.1 module** (OpenSSL provider, Java SunPKCS11), which let existing key-management and TLS/code-signing stacks use vault-held keys with no application change. Keys whose policy requires WebAuthn step-up fail closed over these interfaces by design.
