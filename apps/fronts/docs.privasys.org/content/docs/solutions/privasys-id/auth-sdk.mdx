title: Auth SDK
description: The browser SDK that adds Privasys ID sign-in and a sealed channel to an attested enclave app, in one call.
---

`@privasys/auth` is the browser SDK a web app drops in to sign people in with Privasys ID and, when the app runs in an attested enclave, to talk to it over a sealed channel. The sign-in surface and the session key live in an iframe on `privasys.id`; the page talks to that iframe over a small typed `postMessage` interface and never sees a key. There is no server-side dependency on the embedding domain.

For a step-by-step integration, read the [tutorial](/tutorials/integrate-auth-sdk).

## What the SDK does

- Signs the user in: wallet ceremony by QR code or push to a paired wallet, with passkey and federated sign-in as configurable alternatives.
- Keeps the user signed in: tokens are held in the iframe on `privasys.id`, renewed silently, and shared by the pages of your site. On a site the person has not used yet, their phone gets a notification, with no QR code to scan.
- Asks for attributes the app declares, with the user's consent in the wallet.
- When the app runs in an enclave, establishes a **sealed session**: AES-256-GCM end to end from the iframe to the enclave, through a gateway that only ever carries ciphertext, with requests, server-sent streams and WebSockets all sealed.
- Keeps that sealed session alive without the user: when the enclave forgets it (idle, restart) the SDK re-establishes it from a voucher the wallet issued at sign-in, and only involves the user again when the enclave's measurement changed.
- Reaches the app with one call whichever way the person signed in: sealed after a wallet sign-in, over the app's direct name otherwise.
- Links a Privasys ID to a person who signed in another way, so the app can ask them to approve an act on their phone.

## Loading it

Either install the package or load the hosted client bundle. Both expose the same `AuthFrame` class.

```html
<script src="https://privasys.id/auth/privasys-auth-client.iife.js"></script>
<script>
  const { AuthFrame } = window.Privasys;
</script>
```

```ts
import { AuthFrame } from '@privasys/auth';
```

The package is published to GitHub Packages. Apps that want one reviewed file in their image can vendor the hosted bundle instead: it holds no keys, and the part of the SDK that runs on `privasys.id` is served by Privasys and updated independently.

## One frame, one call

Create **one** `AuthFrame` for the life of the page and call `connect()`:

```ts
const frame = new AuthFrame({
  apiBase: 'https://api.privasys.org',
  authOrigin: 'https://privasys.id',
  rpId: 'privasys.id',
  clientId: 'my-app',                       // from your relying-party registration
  appName: 'My App',
  brokerUrl: 'wss://relay.privasys.org/relay',
  scope: ['openid', 'offline_access'],
  sessionRelay: { appHost: 'my-app.apps.privasys.org' },  // your enclave app
  container: document.getElementById('gate'),
  presentation: 'page',
  methods: ['wallet'],
  pitch: { title: 'Your data, sealed.', bullets: ['Nothing leaves the enclave in the clear.'] },
  app: { displayName: 'My App', logoUrl: 'https://my-app.example/logo.svg' }
});

const { accessToken, session } = await frame.connect();
```

`connect()` does whichever of these the situation needs, in order, and resolves once the app has what it asked for:

1. **Silent restore.** An existing Privasys ID session (SSO) and, with `sessionRelay`, the sealed session re-established from the stored voucher. No UI.
2. **One-tap re-approval.** The session exists but the enclave refused the voucher because its measurement changed (the app was updated, or the platform under it). The gate asks for one approval in the wallet and explains what changed.
3. **Sign-in.** The full ceremony, rendered in `container` per `presentation`.

It rejects with a `ConnectError` whose `code` is `cancelled`, `timeout` or `failed`. To retry, call `connect()` again on the same frame.

| Option | Meaning |
| --- | --- |
| `sessionRelay.appHost` | The enclave app's platform hostname. Always the platform name, never a custom domain the page may be served from. |
| `scope`, `attributes` | What the sign-in asks for. Ask for the minimum: an attribute the user must first add to their wallet turns a returning visit into an onboarding. |
| `presentation` | `page` renders the whole gate in your container; `inline` a compact column; `modal` an overlay. |
| `methods` | Restrict to `wallet`, `passkey` or `social`. A sealed session needs the wallet, so enclave apps set `['wallet']`. |
| `providers` | Narrow the `social` list to some of `github`, `google`, `microsoft`, `linkedin`, in that order. `methods: ['social'], providers: ['microsoft']` shows a single "Sign in with Microsoft" button and no chooser. It only narrows the list the identity provider publishes; a name it does not have is left out, and a list that matches nothing falls back to the published one. |
| `theme` | Style the gate within a closed set of tokens: `font` (a font stack), `colours` (hex only: `text`, `background`, `border`, `focus`, `focusText`, `primary`, `primaryText`, `secondary`, `secondaryText`, `link`), `radius` (0 to 24). A value outside its rule is dropped. The "Secured by Privasys ID" seal stays in every theme. |
| `legal` | `false` hides the terms line in `inline` and `page` presentations, for a page that carries its own terms. A modal keeps it. |
| `audience` | The audience of the access token issued at sign-in, for an app that authorises on it. A direct name passes `app:<app id>` (32 hex characters), which the identity provider grants a client registered for that app. This first token is the only one that can carry the person's name and email, and `getTokenForAudience()` returns it while it is valid; see [the profile headers](#the-persons-name-and-email). |
| `direct` | Also serve people who sign in without the wallet, over the app's direct name; see [one call for both ways](#one-call-for-both-ways-to-reach-your-app). |
| `pitch`, `app` | Plain strings and an https logo, rendered by the SDK in its own styling. |
| `headless` | Draw the gate yourself; see [a headless gate](#your-own-design-a-headless-gate). |

## Your own design: a headless gate

A page built on a design system of its own can draw the sign-in buttons itself. Pass `headless` and the frame stays invisible: it still holds every credential and runs every flow, and the page draws the options, starts the one the person picks, and narrates its progress.

```ts
const frame = new AuthFrame({
  apiBase: 'https://api.privasys.org',
  clientId: 'my-app',
  appName: 'My App',
  scope: ['openid', 'email', 'profile', 'offline_access'],
  headless: {
    onOptions: (options, gate) => drawButtons(options, (choice) => gate.start(choice)),
    onState: (s) => narrate(s),
  },
});

const { accessToken } = await frame.connect();
```

| Callback | What it receives |
| --- | --- |
| `onOptions(options, gate)` | What the client offers: `own` (the client's [own registrations](/tutorials/entra-sign-in), such as an organisation's staff sign-in, each with its display name), `providers` (the platform's, each with `id`, `name` and a brand `icon`), `wallet` (Privasys ID is offered), `push` (this device can be notified) and, when the browser remembers several phones, `wallets` (each with an `id` and a `label`, the most recently used first: draw one button each). Called again for every new attempt. `gate.start(choice)` starts `{ method: 'social', provider, own?, chooseAccount? }` or `{ method: 'wallet', qr?, wallet? }`, where `wallet` is the `id` of the phone to notify and `chooseAccount: true` has Google, Microsoft or GitHub show its own account picker; the frame starts only a choice it offered. `gate.cancel()` stops the attempt. |
| `onState(state)` | Where the attempt is: `authenticating`, `push-waiting` (while a push waits, `start({ method: 'wallet', qr: true })` switches to the QR code), `qr-scanning` with the code as `qrSvg`, `success`, and `error` with `error`. |

A social sign-in opens its popup on `privasys.id`, at the address the frame names, from the click on your page; the SDK does this for you. Set every label as text and show `qrSvg` as an image, never as markup. Passkeys are not offered headless, because a passkey ceremony needs the click inside the frame: use the visible gate where passkeys matter. With `headless`, `container`, `presentation`, `pitch`, `theme` and `legal` have no effect.

A complete page in the style of the GOV.UK Design System is in the repository: [`sdk/examples/headless`](https://github.com/Privasys/identity-platform/tree/main/sdk/examples/headless).

## The page's origin

The result of a sign-in goes to the page that runs it, so the identity provider checks that page's origin against your client: the origin of one of its redirect URIs, or one of its registered page origins (`PUT /api/v1/oauth-clients/{client_id}/origins`, for the client's owner). Register every origin your pages are served from, including a custom domain.

## The sealed session

With `sessionRelay` set, `connect()` resolves with a `SealedSession`. The session the app gets carries the user's identity: the enclave asserts it to the app as the `X-Privasys-Sub` header on every request, so the app never handles a token on this path. The subject is your client's own for that person (see [Subjects: one per application](/solutions/privasys-id/idp#subjects-one-per-application)): stable for you, and meaningless to any other application.

```ts
const r = await session.request('GET', '/api/v1/me');      // { status, headers, body: Uint8Array, sealed }
const s = await session.stream('POST', '/v1/chat', body);  // ReadableStream of plaintext bytes (SSE etc.)
const ws = session.openWebSocket('/api/v1/events');        // sealed both ways; ready, send, onMessage, onClose
```

Every body leaves the browser as ciphertext in `application/privasys-sealed+cbor`. The HTTP status in `request()` is the app's own status, carried inside the sealed envelope. An **unsealed** 401 is different: it means the enclave no longer knows the session, and the SDK handles it itself (next section).

### Liveness

A sealed session reports its state and survives its own recovery. Keep using the same object; never rebuild your transport on an error.

| `session.state.status` | What it means | What the app does |
| --- | --- | --- |
| `ok` | Requests flow. | Nothing. |
| `recovering` | The enclave forgot the session (idle timeout, restart) and the SDK is re-establishing it from the voucher. `reason` names a transient obstacle (`unavailable`, `rate-limited`). | Show "reconnecting" if you like. A request made meanwhile may fail; the next one retries. |
| `reapproval-required` | The enclave refused the voucher. `reason` says why: `workload-changed` (the app was updated), `enc-changed` (the platform changed), `voucher-expired`, `voucher-invalid`, `no-voucher`. | Call `frame.connect()` again. The gate runs the one-tap approval; the session object keeps working afterwards. |
| `signed-out` | The Privasys ID session ended. | Call `frame.connect()` again; it signs the user in. |

```ts
session.onState((s) => {
  if (s.status === 'reapproval-required' || s.status === 'signed-out') {
    void frame.connect({ container: gateElement }); // the gate you just mounted
  }
});
```

A sealed WebSocket refused because the enclave forgot the session is re-opened by the SDK on the recovered session, queued sends intact. Create one `AuthFrame` per page and per enclave host (`sessionRelay.appHost` is fixed at construction); the SDK warns when a second one for the same host is alive.

## One call for both ways to reach your app

An app that also serves people who sign in without the wallet has two ways in: the sealed session for wallet users, and its [direct name](/solutions/platform/developer-platform/custom-domains#private-routes-for-signed-in-users) with an access token for everyone else. Set `direct` and call the frame; it takes the right one.

```ts
const frame = new AuthFrame({
  // ...as above
  sessionRelay: { appHost: 'my-app.apps.privasys.org' },
  direct: { audience: 'app:<app id hex>' },   // origin defaults to the page's own
});

const { transport } = await frame.connect();               // 'sealed' | 'direct' | null
const r = await frame.request('GET', '/api/v1/me');        // { status, headers, body: Uint8Array, transport }
const s = await frame.stream('POST', '/v1/chat', body);
const ws = frame.openWebSocket('/api/v1/events');
```

| Who signed in | What `frame.request()` does |
| --- | --- |
| With the wallet | Uses the sealed session. A wallet user is never moved to direct: when the sealed session needs re-approval, the call fails until `connect()` restores it. |
| With a passkey, Google, Microsoft, GitHub or LinkedIn | Sends the request over HTTPS to `direct.origin` with an access token for `direct.audience`. |

Your app receives the same identity headers either way, and `X-Privasys-Transport` tells it which way a request came. Its manifest must declare `"direct": "private"` for the private routes to answer on the direct name.

A direct WebSocket carries the token in the handshake, which the enclave verifies and removes before your app sees the request. It closes when the token expires, after about an hour: open a new one on close, as you would for a sealed socket.

## The person's name and email

When a client has registered `email` and `name` as required attributes, the enclave asserts them to the app beside the subject, on a direct name and on a sealed session:

| Header | Value |
| --- | --- |
| `X-Privasys-Sub` | the user's subject for your app |
| `X-Privasys-Email` | the token's `email` claim, only when the address was proved |
| `X-Privasys-Name` | the token's `name` claim, percent-encoded UTF-8: decode it before use |

The runtime strips these from every inbound request, so only it can set them.

The identity provider stores no user profile, so only the token from the sign-in itself carries these claims. A token renewed by refresh names the subject alone. **Store them the first time you see them, keyed by the subject.** An app that missed them (a session restored from storage, say) sees no headers and asks the person to sign in again when it needs the profile.

An address is proved when the person signs in directly with a provider that vouches for it (Google's `email_verified`, GitHub's primary address, Microsoft's `xms_edov` claim saying the domain is verified by the person's tenant, or an organisation's [own Entra registration](/tutorials/entra-sign-in) on a named tenant). Through the wallet, it is proved when the wallet hands over a disclosure from the [Privasys Attribute Verifier](/solutions/privasys-id/verifiers), which checked the provider's own signed token under the same rules, or mailed a code to the address itself. Otherwise no email header is sent: ask the person, and check the address yourself.

## Staying signed in

A session belongs to one client and is held in the iframe's storage on `privasys.id`. Browsers keep that storage separately for each site that embeds the iframe, so:

| Where the person goes next | What happens |
| --- | --- |
| Another page of your site, same client | Signed in already. Pages on subdomains of one registered domain count as one site. |
| Another client on the same site | A sign-in of its own. A page is only ever given the session of a client that registered its origin. |
| A site on another domain | A sign-in of its own, by notification when the browser knows the person's phone (below). |

`frame.clearSession()` signs the person out of your client on your site. The IdP takes no part in deciding who is signed in where; while a session is open it holds that session's renewal token, which it deletes at sign-out.

Because pages share a session, its renewal is coordinated across documents by the SDK. Create one `AuthFrame` per page; the SDK warns when a second is alive, because frames created and destroyed around each other are how a renewal is lost.

### One QR code per browser

After a wallet sign-in the gate asks "Trust this device?". A person who agrees is remembered by `privasys.id` itself, in that browser. On a site they have never used, pressing the Privasys ID button opens a small `privasys.id` window for a moment to read that, and their phone gets a notification. They scan a QR code once per browser, not once per site.

The window opens from the person's click, so start sign-in from a click. A headless page gets the same behaviour: the SDK opens the window for it. A site that sets `Cross-Origin-Opener-Policy: same-origin` cuts the window off from the page, and the gate shows the QR code there.

### Several phones, several accounts

- **Several phones.** A browser can remember more than one Privasys ID. The gate then lists them by the name the wallet gives the phone, with "Forget" beside each and "Use another Privasys ID" for a new one. Signing out keeps the list.
- **Several provider accounts.** Google, Microsoft and GitHub sign a person straight in when one account is active in the browser. "Use another account" on the gate has the provider show its own account picker. The gate keeps no list of accounts.

## Linking a Privasys ID to another sign-in

People who sign in to your app with Microsoft or Google can add their Privasys ID to that account, so your app can ask them to [approve an act on their phone](/solutions/platform/developer-platform/wallet-approvals). The link returns their Privasys ID subject under your client and leaves the session they are in untouched.

```ts
// 1. Your server makes a single-use nonce for this person's session.
const { nonce } = await (await fetch('/link/start', { method: 'POST' })).json();

// 2. From a click: a modal limited to the Privasys ID wallet.
const { idToken } = await frame.linkIdentity(nonce);

// 3. Your server verifies the token and stores its subject.
await fetch('/link/finish', { method: 'POST', body: JSON.stringify({ idToken }) });
```

The nonce is 16 to 256 URL-safe characters. Your server accepts the ID token only when all of these hold:

| Check | Value |
| --- | --- |
| Signature | A key from `https://privasys.id/jwks` |
| `iss` | `https://privasys.id` |
| `aud` | Your client id |
| `exp` | In the future (the token lives 15 minutes) |
| `nonce` | The one your server made for this session, not used before |
| `amr` | Contains `"webauthn"`: the person answered with a Privasys ID, not through another provider |

`sub` is then the person's Privasys ID under your client: store it beside their account and address approvals to it. It is the same subject they would have if they signed in to your client with their Privasys ID directly.

No session is kept for the linked identity and its access token stays in the frame. The person sees your app in their wallet from then on; removing it there ends the link, and approvals stop reaching them.

## Attribute consent

When the app declares attributes, the wallet shows a consent screen during sign-in and the user chooses what to share. Granted attributes flow into the JWT for that sign-in; refreshing the token does not re-include them. See the [IdP page](/solutions/privasys-id/idp#refresh-tokens) and the [attribute marketplace](/solutions/privasys-id/attribute-marketplace) for government-verified claims.

## Trust scope of the iframe

The iframe lives on `privasys.id`. The page cannot read its storage, its WebCrypto keys or its session table; it talks to the iframe only over `postMessage`. The sealed session's key and the SDK's ephemeral private key never cross that boundary: the page submits plaintext and receives plaintext, and sealing happens inside. The trust argument, including why the gateway can terminate TLS without seeing anything, is on [Technology > Sealed Session](/technology/sealed-session).
