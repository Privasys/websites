---
title: X.509 OID Scheme
description: Reference of the Privasys X.509 OID scheme (version 2) carried by RA-TLS certificates on Enclave OS Mini and Enclave OS Virtual, and of the evidence type identifiers used by the evidence exchange.
---

All Privasys OIDs live under the Private Enterprise Number arc `1.3.6.1.4.1.65230`. The scheme is shared across both Enclave OS editions so that [verification libraries](/solutions/platform/verification-libraries) work regardless of the TEE backend. This page describes scheme version 2, which accompanies [RA-TLS version 2](/solutions/enclave-os/attestation/ra-tls).

The rules of the scheme:

- **One slot, one meaning, on both editions.** A number never means one thing on Enclave OS Mini and another on Enclave OS Virtual.
- **Numbers are contiguous within an arc, and a retired slot is never reused.**
- **Evidence is never a certificate extension.** The DCAP quote and any GPU evidence are served by the [evidence exchange](/solutions/enclave-os/attestation/ra-tls#the-evidence-exchange) on the connection, not embedded in the certificate. Arc 8 only names the evidence types.
- **The app-defined sub-arc root (`5.4`) never carries a value.** Apps publish under it, never at it.

The "v1" column in each table maps the slot to its number in the previous scheme, for reading old certificates and old records. The SDKs parse version 2 only, and a certificate that still carries a version 1 quote extension is rejected as a version 1 leaf.

## Arc 1, Platform identity

What runs here, and which instance.

| OID | Name | Encoding | Mini | Virtual | v1 |
|-----|------|----------|------|---------|----|
| `1.1` | Runtime Version Hash | 32 bytes, SHA-256 of the runtime version (Wasmtime on Mini, containerd on Virtual) | yes | yes | 2.4 |
| `1.2` | Image Profile | UTF-8 string, `"production"` or `"dev"`, read from the dm-verity-measured marker `/etc/privasys/image-profile`. Verifiers reject `dev` unless explicitly opted in. | yes | yes | 2.8 |
| `1.3` | Enclave Instance ID | 16-byte UUID, the management-service enclave id received at registration | yes | yes | new |
| `1.4` | Platform Hardware Identity | reserved for platform ownership endorsements | no | no | new |

## Arc 2, Platform configuration

| OID | Name | Encoding | Mini | Virtual | v1 |
|-----|------|----------|------|---------|----|
| `2.1` | Config Merkle Root | 32 bytes, root of the platform [configuration tree](/solutions/enclave-os/attestation/merkle-tree) over every configuration input of the platform | yes | yes | 1.1 |
| `2.2` | Egress CA Bundle Hash | 32 bytes, SHA-256 of the outbound trust-anchor bundle | yes | no | 2.1 |
| `2.3` | Attestation Servers Hash | 32 bytes, SHA-256 of the sorted attestation server URL list | yes | yes | 2.7 |

## Arc 3, Platform keys and state

Key origin and authenticated state of the platform.

| OID | Name | Encoding | Mini | Virtual | v1 |
|-----|------|----------|------|---------|----|
| `3.1` | Data Encryption Key Origin | UTF-8 string, `"byok:<fingerprint>"` or `"generated"` (`"vault:<handle>"` on vault-keyed machines) | no | yes | 2.6 |
| `3.2` | Authenticated State Root | 40 bytes, the 32-byte [Merkle store](/solutions/enclave-os/enclave-os-mini/merkle-store) root followed by a big-endian u64 version | yes | no | 2.6 |

Slot `2.6` of version 1 meant the key origin on Virtual and the state root on Mini. Version 2 gives each its own slot.

## Arc 4, Workload identity

Which app, and which code. These extensions appear in certificates served via [SNI routing](/solutions/enclave-os/attestation/ra-tls#per-workload-certificates-and-sni-routing): each workload (WASM app in Mini, OCI container in Virtual) gets its own leaf certificate.

| OID | Name | Encoding | Mini | Virtual | v1 |
|-----|------|----------|------|---------|----|
| `4.1` | Workload App ID | 16-byte UUID, the management app id (`apps.id`). Pins *which* app a workload is: a vault key can be sealed to a specific app (MR_APP) so a same-code peer with a different app id cannot unseal it, dependents select the matching [dependency entry](/solutions/enclave-os/attestation/dependencies) by it, and clients read the app id straight off the attested leaf. Stamped by the measured runtime, never self-declared by the workload. Omitted when no app id is supplied (MR_ENCLAVE). | yes | yes | 3.6 |
| `4.2` | Workload Code Digest | 32 bytes, SHA-256 of the WASM bytecode (Mini) or of the OCI manifest (Virtual) | yes | yes | 3.2 |
| `4.3` | Workload Image Ref | UTF-8 string, image reference without digest | no | yes | 3.3 |

## Arc 8, Evidence types

Identifiers for the evidence bodies served by the post-handshake [evidence exchange](/solutions/enclave-os/attestation/ra-tls#the-evidence-exchange). They name the `tee` value of an attest response and are never certificate extensions.

| OID | Name | `tee` | v1 |
|-----|------|-------|----|
| `8.1` | Intel SGX DCAP quote | `sgx` | `1.2.840.113741.1.13.1.0` as a certificate extension |
| `8.2` | Intel TDX DCAP quote | `tdx` | `1.2.840.113741.1.5.5.1.6` as a certificate extension |
| `8.3` | AMD SEV-SNP report | `sev-snp` | `4.1`, never emitted |
| `8.4` | NVIDIA GPU CC evidence | `nvidia-gpu` | `5.1` |

A GPU workload answers with `tee: "tdx-gpu"`: a TDX quote plus a `gpu_evidence` body, cross-committed through `report_data`.

## Prefixes

| Prefix | Description |
|--------|-------------|
| `1.3.6.1.4.1.65230.` | The whole Privasys private-enterprise arc. Membership of an extension in the verified set is by arc, not by allowlist. |
| `1.3.6.1.4.1.65230.5.4.` | The sub-arc apps publish attested digests under, through the SDK `set-attestation-extension` call. |

## Verification Strategies

The extensions identify; the evidence exchange proves. A certificate on its own says which runtime, workload and configuration the enclave claims to be running; the quote returned by the evidence exchange proves that the certificate's key was generated inside a TEE with specific measurements, and in challenge mode that the quote belongs to this connection. Extension values are only meaningful once that proof has passed, because the measured runtime that stamps them is what the quote attests.

In addition to the [Configuration Merkle Tree](/solutions/enclave-os/attestation/merkle-tree) roots (`2.1` for the platform, `5.1` for a workload), both editions embed individual extensions for common properties. This gives clients two complementary approaches:

- **Full audit**: request the configuration manifest and recompute the Merkle root to verify all inputs.
- **Fast-path**: check a single extension (for example, "does the workload code digest match my expectation?") without any Merkle computation.

| Strategy | What to check | What it proves |
|----------|---------------|----------------|
| **Code identity only** | Quote measurements from the evidence exchange, `report_data` against the leaf key | Correct runtime binary or image and a key inside it, but configuration unknown |
| **Code + Merkle root** | Evidence + `2.1` (and `5.1` on a workload leaf) | Code and full configuration verified |
| **Fast-path OIDs** | Evidence + specific extensions (`4.1`, `4.2`, `6.1`, `1.2`, ...) | Individual properties without a full Merkle audit |
| **Full manifest audit** | Request the manifest, recompute `2.1` or `5.1` | Complete transparency of all inputs |

See [RA-TLS Certificates: Verification](/solutions/enclave-os/attestation/ra-tls#verification) for the step-by-step verification flow.
