---

Every application deployed on the Privasys Platform receives its own hostname under `*.apps.privasys.org`. Traffic reaches the right enclave through the **platform gateway**, a small routing layer that runs on its own machines, outside any enclave. The gateway is operated by Privasys and is not attested, so the design keeps it out of the data wherever a client can verify the enclave itself, and makes the remaining cases explicit: declared by the application, measured, and visible to anyone who checks the attestation.

A connection reaches an application over one of two legs. The client chooses which:

| Leg | TLS ends at | What the gateway sees | Who uses it |
| --- | --- | --- | --- |
| **RA-TLS splice** | the enclave | the SNI hostname only | the wallet, the CLI, services built on the [verification libraries](/solutions/platform/verification-libraries), other enclaves over mutual RA-TLS |
| **Gateway-terminated** | the gateway, with a publicly trusted certificate | TLS metadata and the path; bodies stay sealed unless the route is a declared surface | browsers through the [auth SDK](/solutions/privasys-id/auth-sdk) (sealed session), and anyone with plain HTTPS on a declared public or static surface |

An application served on its **own domain** uses a third path: the gateway splices that hostname to the enclave for every client, and the enclave answers browsers with a publicly trusted certificate it obtained itself. The gateway sees the hostname only. See [your own domain](/solutions/platform/developer-platform/custom-domains).

The splice leg is the one to use whenever the client can verify an RA-TLS certificate. Browsers and third-party machines cannot: they refuse the enclave's attestation-bearing certificate, and only a publicly trusted certificate gives them a padlock. The terminated leg exists for them.

## The RA-TLS splice leg

```
Client ──TLS ClientHello──► Gateway (L4) ──TCP──► Enclave Machine
                              │                     (SGX or TDX)
                              │ polls routes
                              ▼
                        Platform API
```

1. A client opens a TLS connection to `myapp.apps.privasys.org`.
2. DNS resolves the hostname to one of the gateway instances (round-robin).
3. The gateway reads the **SNI hostname** from the TLS ClientHello message.
4. It looks up the hostname in its routing table and finds the target enclave machine.
5. The gateway opens a TCP connection to the enclave and **splices** the two connections together, forwarding raw encrypted bytes in both directions.
6. The TLS handshake completes end-to-end between the client and the enclave. The gateway is never part of the TLS session.

On this leg the gateway adds approximately one round trip of latency (1 to 5 ms within a region) for the initial connection. Once established, the stream splice has zero per-byte overhead, and the gateway holds nothing it could read.

## The gateway-terminated leg

```
Browser ──public TLS──► Gateway ──RA-TLS, policy-checked──► Enclave
                          │
            sealed bodies pass through opaque;
            declared surfaces pass through in the clear
```

1. The gateway terminates the public TLS handshake with a publicly trusted certificate for `*.apps.privasys.org`.
2. On its internal leg it opens an RA-TLS connection to the enclave and verifies the enclave's certificate against the control plane's attestation policy for that route. A mismatch aborts the connection. A client on this leg therefore knows that the gateway refused to forward to an enclave that did not match the policy. We call this **gateway-vouched** attestation: it is trust in Privasys operations, the same tier as a non-wallet sign-in, and it is never the same as verifying the hardware yourself.
3. Requests are reverse-proxied across the internal leg. By default the body is opaque to the gateway: a [sealed session](/technology/sealed-session) encrypts it under a key the gateway never sees, and the enclave refuses application requests that arrive in the clear on this leg with `403 sealed-transport-required`. A front-end regression cannot silently downgrade the data plane.
4. The exception is an application's **declared surfaces**: a static shell (GET and HEAD on declared prefixes) and explicit public routes, declared in the application's measured manifest. On those routes the gateway reads the request and the response in full. The enclave runtime serves them anonymous by construction: it drops every credential and identity header before the application sees the request, never asserts an identity, and refuses to load an image that declares a priced endpoint public. Because the declaration is part of the measured image, the application's attestation tab and its store listing show exactly which routes are served in the clear. See [Surfaces](/solutions/platform/developer-platform/deploy-container#surfaces-private-static-and-public) for the declaration and the rules.

**What the gateway logs.** On both legs the gateway logs TLS metadata and route outcomes only: a failed handshake with the client address and the SNI, an upstream that could not be reached, a quarantine refusal. It never logs a header, a query string or a body, and it keeps no copy of anything that passed through it. Traffic on a declared surface transits the gateway and nothing more.

## What the gateway does not do

The gateway is deliberately minimal:

- **No key for your application.** The enclave holds its own RA-TLS key. The gateway holds only the public wildcard certificate for the terminated leg, which cannot impersonate the enclave on the splice leg.
- **No reading of private traffic.** On the splice leg it forwards encrypted bytes. On the terminated leg it forwards sealed bodies. It reads traffic only on the surfaces an application declared in the clear.
- **No notion of your application's paths.** On the splice leg it does not parse HTTP at all. On the terminated leg it reverse-proxies without a route table of its own: it learns that a response was public from the enclave runtime, which is the only party that knows the manifest.
- **No caching, no rate limiting.** Public routes are rate-limited per client inside the enclave runtime, and nothing of ours caches a response.
- **No session state.** Every gateway instance is stateless and interchangeable. There is no sticky routing.
- **No authentication at the gateway layer.** Authentication and authorisation happen inside the enclave, enforced by RA-TLS, the sealed session and OIDC.

## Route synchronisation

Each gateway instance polls the platform API for the current routing table:

```
GET /api/v1/internal/routes
Authorization: Bearer <token>
If-None-Match: "sha256:abc123..."
```

The platform returns a list of `(sni, upstream)` pairs derived from all currently deployed applications. Routes are updated atomically in memory. The gateway uses **ETag-based polling**, so unchanged route tables return `304 Not Modified` with no body.

A route may also carry a `state`. A route without one is active; `"state": "quarantined"` marks an application whose enclave is paused (see [Quarantined applications](#quarantined-applications)):

```json
{ "sni": "myapp.apps.privasys.org", "upstream": "203.0.113.10:8445", "state": "quarantined" }
```

When an application is deployed or undeployed through the [Developer Platform](/solutions/platform/developer-platform), the routing table updates automatically. No manual DNS or gateway configuration is needed.

## Multi-region availability

Multiple gateway instances run across geographically distributed regions. DNS resolves `*.apps.privasys.org` to all available gateways using round-robin A records. Because every instance is stateless and syncs the same routing table, failover is automatic: if one gateway becomes unavailable, DNS health checks route traffic to the remaining instances.

| Region | Location |
|--------|----------|
| Europe West (Paris) | `europe-west9-a` |
| Europe West (London) | `europe-west2-a` |

## Unknown hostnames

If a client connects with an SNI hostname that does not match any deployed application, the gateway completes a TLS handshake using an ephemeral self-signed certificate and returns an **HTTP 404** response. This provides a clear signal to the client rather than silently dropping the connection.

## Quarantined applications

Every enclave keeps a [trusted time](/solutions/enclave-os/trusted-time) that it checks against the platform monitor and NTS servers. When the monitor finds an enclave whose host clock is wrong, or one it cannot check, it asks the platform to quarantine that enclave. Every application route on the enclave is then marked `quarantined`, and each gateway applies it on its next route sync, within about 5 seconds. Because the gateways run on their own machines, the enclave's host cannot bypass the quarantine for traffic that comes through them.

A quarantined route is never dialled. Clients get a clear refusal instead of the 404 of an unknown hostname:

- **HTTPS clients the gateway serves directly** (browsers, and SDKs using the [sealed session](/technology/sealed-session)) receive `503 Service Unavailable` with `Retry-After: 300` and `Cache-Control: no-store`. API clients get a JSON body, and browsers loading a page get a short HTML page with the same message. CORS preflights are still answered, so a cross-origin SDK can read the refusal.

  ```json
  {"error":"enclave_quarantined","message":"This application is temporarily unavailable while its enclave's clock is checked."}
  ```

- **RA-TLS clients** (those advertising the `privasys-ratls/1` ALPN, whose TLS session belongs to the enclave) receive a fatal TLS `handshake_failure` alert, and the connection closes.

Connections already open when the quarantine arrives are closed, including streamed responses and WebSockets, so a long-lived session does not keep talking to a paused enclave. The enclave itself keeps running, and its manager hostname stays routed so the monitor can keep checking it. When a poll comes back clean, the monitor releases the quarantine and the next route sync serves the application again.

## Application hostnames

Every application deployed through the Developer Platform automatically receives a hostname:

```
<app-name>.apps.privasys.org
```

This hostname is usable immediately after deployment. No DNS configuration is required from the developer. The platform registers the route and all gateway instances pick it up within seconds.

## Connecting to your application

Which leg a client lands on depends on what it can verify, and on the route.

**Attested clients** use an [RA-TLS client library](/solutions/platform/verification-libraries) and verify the attestation during the handshake. The gateway splices the connection and sees only the SNI:

```python
from ratls_client import RaTlsClient

client = RaTlsClient("myapp.apps.privasys.org", 443)
response = client.get("/api/hello")
```

**Browsers** reach private routes through the [auth SDK](/solutions/privasys-id/auth-sdk), which opens a [sealed session](/technology/sealed-session) over the terminated leg. The page gets a normal padlock; the bodies stay sealed to the enclave.

**Plain HTTPS clients** such as `curl`, a webhook sender or an OAuth redirect can reach the routes an application declared as public or static. The response says which leg served it:

```sh
curl -i https://myapp.apps.privasys.org/api/v1/public/status
```

```text
HTTP/2 200
content-type: application/json
x-privasys-transport: public

{"status":"ok"}
```

Every other route refuses a request that arrives in the clear:

```sh
curl -i https://myapp.apps.privasys.org/api/v1/me
```

```text
HTTP/2 403
content-type: text/plain; charset=utf-8

sealed-transport-required
```

A plain TLS client cannot complete the handshake on the splice leg, because the enclave presents an RA-TLS certificate with hardware attestation extensions rather than a certificate signed by a public CA. That is why public and static surfaces are served on the terminated leg.
